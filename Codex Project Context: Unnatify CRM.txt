## 1. Purpose of This Document

This document is the living source of truth for Codex and any AI/code assistant working on the Unnatify CRM project. Keep this updated whenever architecture, tools, database schema, workflows, deployment, UI rules, or integration decisions change.

Codex should read this document before making code changes.

---

## 2. Product Summary

Unnatify CRM is an automation-first CRM and lead conversion platform designed for loan/admission-style customer journeys. The system should manage leads, automate outreach through WhatsApp and voicebot journeys, capture customer intent, route interested leads to human agents/partners/branches, and track all actions through activities, tasks, logs, and audit trails.

The product is not only a CRM. It is a combination of:

* Lead management system
* Workflow automation platform
* WhatsApp communication platform
* Voicebot orchestration system
* Telephony-connected CRM
* Task and follow-up management system
* Admin operations and audit platform

There is no Opportunity module needed at this stage.

---

## 3. Core Business Requirement

The system should support a journey like this:

1. Admin uploads leads.
2. System validates uploaded leads.
3. Leads are distributed branch-wise / team-wise / partner-wise.
4. Automation starts from the lead upload date.
5. First WhatsApp loan/offer message is triggered.
6. Reminder is sent after a configured gap, such as 10 days.
7. Follow-up automation continues based on customer behavior.
8. Voicebot call is triggered when required.
9. Customer intent is captured from WhatsApp replies or voicebot responses.
10. Leads are categorized into buckets such as Hot, Warm, Cold, Not Interested, Expired, Converted.
11. Interested/qualified leads are assigned to partner/branch/agent users.
12. Human follow-up happens through task and activity management.
13. Automation stops when converted, expired, opted out, wrong number, not interested, or max attempts reached.

## 8.4 Users, Roles, Teams, Sales Groups

Required modules:

* Users
* Roles
* Teams
* Sales Groups
* Permission Templates

User should belong to:

* Exactly one team
* One or more sales groups if needed
* One role
* One permission template or derived permission set

Initial fixed roles:

* Administrator
* Sales Manager
* Sales User

Sales Groups are required and are used for sales-side grouping and assignment logic.

Teams are configurable and should represent business groupings such as branches, partners, admin teams, or operational teams. Branch Manager, Partner, and similar business labels should be modeled as Teams/configuration, not as fixed roles unless explicitly changed later.

Users can have custom fields. User-level custom fields can be used in assignment rules.

Assignment rule conflict behavior:

```txt
If multiple assignment rules match, the rule with the lowest priority number wins.
Example: priority 1 runs before priority 2.
If multiple matching rules have the same priority, the older rule wins.
If no rule matches, the lead remains unassigned.
```

## 9. Connector Requirements

MCUBE is the selected provider for WhatsApp, voicebot, and telephony/click-to-call integrations.

MCUBE technical documentation, webhook payload samples, authentication details, and sandbox/test credentials will be provided later. Connector implementation should keep provider-specific mapping isolated so MCUBE payloads, statuses, and dispositions can be normalized into the CRM data model.

## 9.1 Telephony Connector

Telephony connector must support:

* Call log posting
* Click-to-call
* Incoming call webhook
* Inbound call route API
* Agent popup
* Call disposition updates
* Call recording URL storage
* Telephony connector configuration UI
* Mail-merge support from Lead and User fields in click-to-call request body

Telephony events should create system Call activities.

Call log fields:

* lead_id
* phone_number
* agent_user_id
* call_direction
* call_status
* call_duration
* recording_url
* provider_call_id
* disposition
* started_at
* ended_at
* raw_payload

Click-to-call flow:

1. User clicks call button on lead.
2. Backend calls telephony provider API.
3. Telephony provider connects agent/customer.
4. Provider posts call log webhook.
5. System creates Call activity.
6. Lead timeline updates.

Agent popup flow:

1. Incoming call webhook received.
2. System identifies lead by phone.
3. Popup event is sent to frontend/agent session if agent is online.
4. Popup appears in all active browser tabs for that logged-in agent.
5. If popup is closed in one tab, it closes from all active tabs for that agent.
6. Agent can view configured lead details in popup or open full lead detail in a new tab.

Agent popup UI should be configurable:

* Configure which lead fields appear in popup
* Configure which lead detail tabs/sections appear in popup
* Include option to open lead in new browser tab
* Store popup events for audit/history
* If agent is offline, store event for recent/missed call notifications later

Inbound call route API requirement:

```txt
Method: GET
Query param: caller_id=<lead_or_caller_phone>
Response content type: text/plain
Response body: agent phone number only
```

Reference pattern with placeholders:

```txt
GET /webhooks/telephony/lead-route?caller_id=9845098450
Response: 9123456789
```

Use clean Unnatify API URLs, not LeadSquared-compatible URL paths with org/access/secret path parameters.

Routing logic should find the lead by caller phone, determine assigned user/team/agent, return the mapped agent phone number, and log the route request. If no lead is found or no assigned/mapped agent number is available, return a blank text response.

Phone format rule:

```txt
caller_id is expected as a 10-digit phone number.
Lead mobile lookup should use the 10-digit stored mobile number.
Returned agent number must also be 10 digits.
```

Agent popup API requirement:

```txt
Method: POST
Content-Type: application/json
Also tolerate application/x-www-form-urlencoded if provider sends legacy format
Response content type: application/json
```

Agent popup request fields may include SourceNumber, DestinationNumber, DisplayNumber, Status, Direction, CallSessionId, CallDuration, and StartTime. Response should return success status, message, and CRM call session id.

Recommended clean endpoint:

```txt
POST /webhooks/telephony/agent-popup
```

Call log complete API requirement:

```txt
Method: POST
Content-Type: application/json
Also tolerate application/x-www-form-urlencoded if provider sends legacy format
Response content type: application/json
```

Call log request fields may include SourceNumber, DestinationNumber, DisplayNumber, StartTime, EndTime, CallDuration, Status, ResourceURL, Direction, and CallSessionId. The system should store the raw payload, normalize the call, link it to lead/user where possible, and create a Call activity only from Call Log Complete.

Recommended clean endpoint:

```txt
POST /webhooks/telephony/call-log-complete
```

Click-to-call configuration should support URL, custom headers, HTTP method, response keyword, request type, data template/body, response type, provider support email, test call option, and request/response logs.

Click-to-call data template/body should support mail merge from Lead and User standard/custom fields.

Mail-merged phone variables must resolve to 10-digit numbers.

For click-to-call, the agent number should be the logged-in user's 10-digit phone number from the user profile.

Example body shape:

```json
{
  "HTTP_AUTHORIZATION": "stored-provider-token",
  "exenumber": "{{user.phone}}",
  "custnumber": "{{lead.mobile}}"
}
```

Real org IDs, access keys, secret keys, and provider tokens must not be committed to source control or stored in plain planning docs. Use environment variables or encrypted connector configuration where needed.

## 10. Automation Engine

Automation must be configurable by admin users.

No default automation workflow should be created or hardcoded. Loan journeys such as Day 0 WhatsApp offer, reminder gap, follow-up, voicebot, assignment, stop conditions, and pause conditions must be created through the configurable automation engine.

Preferred UI:

* Node-based visual workflow builder
* Drag-and-drop nodes
* Connectors between nodes
* Easy to create and modify
* LeadSquared-style configurable journey builder
* Clicking `+` should add a new node
* If/else and multi-condition if/else nodes
* Delete node option
* Clone node option
* Configurable workflow-level exit conditions without requiring a separate node

Automation should support:

### Triggers

* Lead uploaded
* Lead created
* Lead updated
* WhatsApp message status changed
* WhatsApp reply received
* Voicebot disposition received
* Call log received
* Task completed
* Time delay reached
* Offer expiry reached

### Conditions

* If lead status equals value
* If lead category equals value
* If WhatsApp reply exists
* If no response after X days
* If voicebot intent equals value
* If branch equals value
* If assigned user exists / does not exist
* If expiry date has passed
* If user custom field equals value
* If lead custom field equals value
* If activity field/custom field equals value
* Multi-condition AND/OR groups

### Actions

* Send WhatsApp message
* Trigger voicebot
* Create task
* Update lead field
* Create activity
* Assign lead using Assignment node
* Stop automation
* Pause automation
* Resume automation
* Mark expired
* Notify user/team
* Call external API using a Postman-like API call builder

Assignment should not run only when a lead is created. The assignment engine must be callable from automation at any stage using an Assignment node. Assignment nodes should support existing assignment rules, inline assignment configuration, reassignment, user/team assignment, lead/user/activity standard and custom fields, run logs, and explanation of why a user/team was selected.

API call action should support method, URL, headers, query params, body, authentication provision, timeout, retries, test call, request/response logs, and mail-merge variables from lead or activity standard/custom fields.

API call node security:

* Only Administrator users can create or edit API-call nodes
* Only HTTPS URLs are allowed
* Block localhost URLs
* Block private/internal IP ranges
* Set request timeout
* Limit retry count
* Log request and response
* Mask secrets/tokens in UI and logs
* Store API-call configuration changes in audit logs

### Stop Conditions

Automation should stop when:

* Lead converted
* Customer not interested
* Customer opted out
* Wrong number detected
* Offer expiry date crossed
* Maximum attempts completed

### Pause Conditions

Automation should pause when:

* Lead assigned to partner
* Callback scheduled
* Human conversation is active
* Verification/application pending

Lead automation report is required. It should show workflow runs per lead and allow drilling into one automation run to see each completed, pending, skipped, failed, or retried step with timestamps, results, and errors.

Admin Operations Center login rules:

* Separate URL such as `/ops-login`
* Separate backend-created ops users
* Username/password login
* Disabled unless at least one ops user exists
* Ops actions should not be audited unless this requirement changes later

## 14. Performance Requirements

System should be optimized for speed and should not break under normal production usage.

Target:

* Frontend initial load under 2 seconds where possible
* API responses under 300 ms for common actions
* Paginated tables everywhere
* No unbounded SELECT queries
* No loading 100k rows into browser
* Use indexes for frequently filtered columns
* Use queues for all delayed/background work
* Use Redis carefully with memory limits
* Add log rotation
* Add DB backup jobs

For KVM 4 VPS:

* Keep Postgres tuned
* Redis memory capped
* BullMQ concurrency controlled
* Avoid heavy analytics on production tables without optimization

## 15. Security Requirements

Security rules:

* Authentication required for all app pages except login
* Initial login should use email and password
* Use Resend for email OTP and password reset email delivery
* Resend API key, verified sender/domain, and from-address should be configured through environment variables or secure settings
* There should be an account-level option to disable 2FA for all users
* Administrators should be able to disable/enable 2FA at individual user level
* Normal users should not be able to disable their own 2FA if admin policy requires it
* Role-based access control
* Field-level permission for User, Lead, and Activity
* Audit logs for all changes
* No public access to Postgres
* No public access to Redis
* Admin/ops pages must not be visible to normal Administrator users and must require separate backend-controlled custom ops login
* Do not expose raw logs publicly
* Mask sensitive fields where required
* Store connector credentials securely in environment variables or encrypted config
* Validate all webhooks
* Rate-limit sensitive endpoints

## 20. Development Rules for Codex

Codex should follow these rules:

1. Do not introduce Kubernetes.
2. Do not introduce PM2 if Docker is used.
3. Use Docker Compose for local/VPS orchestration.
4. Keep services separated: frontend, backend, workers, postgres, redis.
5. Do not expose Postgres or Redis publicly.
6. Use pagination for all list APIs.
7. Do not create arbitrary SQL execution pages.
8. DB viewer must be read-only and table-whitelisted.
9. All automation/system changes must be attributed to System user.
10. Every module must write audit logs for create/update/delete/assignment/status changes.
11. Long-running jobs must go through BullMQ workers.
12. Connector webhooks must store raw payloads for debugging.
13. UI should follow Material Design 3 / Material Expressive style.
14. Keep UI compact and intuitive.
15. Do not add unnecessary complexity or overengineering.
16. Prefer clear, maintainable code over clever abstractions.
17. Add proper error handling and logs.
18. Make the system scalable but not overbuilt for day one.
